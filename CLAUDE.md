# CLAUDE.md — spotify-sync

Cloudflare Worker (TypeScript) + D1 that syncs recently played Spotify tracks and maintains Liked Songs, a frequent-plays playlist, per-artist playlists, history playlists and email digests, with an owner dashboard (log in with Spotify, settings, activity, history import). See README.md for what each job does and the operational runbooks.

## Commands

```bash
npm test              # vitest via @cloudflare/vitest-plugin (local simulated D1/R2/Workflows; never remote)
npm run typecheck     # Worker (tsconfig.json) + scripts (tsconfig.scripts.json)
npm run configure     # deploy.config.json (or DEPLOY_CONFIG / --config) -> wrangler.generated.toml
npm run dev           # configure + wrangler dev --env test (dry_run, remote TEST D1); dashboard: -- --port 8788 --var PUBLIC_URL:http://127.0.0.1:8788
npm run deploy        # configure + deploy to production; normally Workers Builds deploys on push to main
npm run token         # optional CLI Spotify login -> refresh token into D1 state (no owner; the dashboard login is the normal path)
npm run import-history -- <dir> [--dry-run]
```

## Config

- `wrangler.toml` is a **template**: per-deployment values are `{{KEY}}` placeholders, except the top-level `name`, a real default (`spotify-sync`) so Workers Builds' name check passes; configure swaps in `WORKER_NAME` when set. `scripts/configure.mjs` (plain Node, no deps) fills them from `--config <file>`, the `DEPLOY_CONFIG` env var (Workers Builds build variable) or `deploy.config.json`, and writes `wrangler.generated.toml` (or `--out`, must be in the repo root). It validates every key and never prints values. Optional lowercase keys: `settings` (-> the `SETTINGS` var as JSON) and `imports` (`false` drops the `# {{#imports}}` blocks: R2 bucket `<WORKER_NAME>-imports`, Workflow `<WORKER_NAME>-import`). `deploy.config.example.json` lists every key.
- Runtime vars are infrastructure only: `WRITE_MODE`, `PUBLIC_URL`, `ALERT_FROM`, `ALERT_EMAIL_TO`, `SETTINGS`. Secrets: `SPOTIFY_CLIENT_ID`, `SPOTIFY_CLIENT_SECRET`, optional `OPENAI_API_KEY`. Everything an owner chooses is a setting; the Worker's own ids (owner, playlists, cursor) live in D1 `state`.
- **Legacy vars are upgrade-only.** `LEGACY_KEYS` in configure.mjs (`SPOTIFY_USER_ID`, `SPOTIFY_*_PLAYLIST_ID`, `TIME_ZONE`, `FREQUENT_MIN_PLAYS`, `AI_EDITOR`) are rendered as vars only while an old deploy config still has them; `importLegacyConfig` (src/runtime.ts, run by `importLegacyOnce` before any job) copies them into `state`/`settings` once and sets `state` `legacy_config:imported`. Never add new reads of them; read settings and `state`.
- Every wrangler command needs `-c wrangler.generated.toml` (npm scripts do it). `scripts/lib.ts` passes it (or `$WRANGLER_CONFIG`, for another instance) and defaults `--db` to that config's production database. Never point a script at an instance by `--db` alone when several configs exist.
- `deploy.config*.json` (except the example) and `wrangler*.generated.toml` are gitignored and must never be committed. Keep owner-specific values (ids, domains, emails, usernames) out of tracked files.
- vitest renders the template with `deploy.config.example.json` into `wrangler.example.generated.toml` (the template's other placeholders aren't valid values). Adding a placeholder means adding it to the example (and to `DEFAULTS` if optional). vitest blanks `OPENAI_API_KEY`, `SPOTIFY_CLIENT_ID` and `SPOTIFY_CLIENT_SECRET` (`test/editor/test-env.test.ts` guards it): tests pass fake credentials and inject fetch.

## Architecture

- `src/index.ts`: `scheduled()` -> `runScheduled` (src/schedule.ts). `fetch()`: `checkOrigin` on every non-GET/HEAD, then `migrateOnce`, `handleAuthRoutes`, `getSession`, `handleImportRoutes`, `handleDashboard`, 404; each handler returns null for paths it doesn't own. Static files in `public/` (email images, `import.js`, `robots.txt`) are served before the Worker. The Worker is public only via its custom domain (`workers_dev` stays off).
- `src/schedule.ts`: maps each cron string to its jobs (`*/10` sync, `0 3` artist-playlists, `0 4` hindi-favorites, `5 8` history-playlists + holiday-playlist + weekly-digest + monthly-recap as separate jobs; `10 3`/`10 4` accepted too). Before jobs: migrations, legacy import, one gate query. No owner -> the `*/10` cron calls `ensureClaimEmail`; no refresh token -> skip all jobs (no failure alerts on a fresh instance). Disabled jobs return `DISABLED`. The daily cron ends with housekeeping (activity > 90 days, expired sessions).
- `src/runtime.ts` `withJob`: migrations, legacy import, **one** settings read, `loadConfig(env, settings)`, the job (with a `SpotifyClient` whose 5xx retries `runScheduled` picks per cron, `retryFor`: the daily crons get `DAILY_RETRY`, 5 s, 30 s and 60 s with at most 2 min per job and then one 1 s retry per request; the sync, `withJob`'s default and every other client get `QUICK_RETRY`, one 1 s retry; a POST is retried at most once, since Spotify may have applied it), alerts (`alertConfig`, gated by the `alerts` setting; `emailConfig` is ungated for digests/account/import emails), activity log, D1 query count.
- **Routes:** `GET /` (landing or home), `GET /login?next=&switch=1`, `GET /claim?k=`, `POST /claim/resend`, `GET /auth/callback` (the **only** OAuth redirect URI: claim, login, reconnect), `POST /logout`, `POST /logout/all`, `GET /reconnect` (302 to `/login` for old alert links), `GET /welcome` (303 to `/?tour=0`) + `POST /welcome/done` (the guided tour, src/dashboard/onboarding.tsx + public/tour.js), `GET|POST /settings`, `GET /activity` (only with the `advanced` setting on; otherwise 303 to `/settings#s-advanced`), `POST /actions/{sync,preview,playlist/recreate}` (redirect to /settings), `/import...`. No `/sync-full` and no `SYNC_FULL_SECRET` anymore.
- **Auth model (src/auth):** the owner is `state` `owner:spotify_id`, pinned by the first account to complete the emailed setup link (single-use 256-bit nonce in `state` `claim`, 7 days, max 3 cron sends, resend 1/hour 5/day, sent only to `ALERT_EMAIL_TO`). `SPOTIFY_USER_ID` (legacy) overrides it while set. Login accepts only the owner and always saves the new refresh token; while `alert_failing:sync` exists it also runs a sync. The claim and every login land on Home (where the guided tour starts) until `state` `onboarding:done` is set (finishing or skipping the tour sets it), then go to `next`. The OAuth state lives in a short-lived cookie (`__Host-oauth`, double-submit, no D1 write). Sessions: random token in `__Host-session` (plain names on an `http://` PUBLIC_URL), D1 `sessions` stores only its SHA-256, 30 days absolute, valid only while it matches the effective owner. CSRF: SameSite=Lax + `checkOrigin` (Origin must equal PUBLIC_URL's origin; absent or `null` Origin falls back to `Sec-Fetch-Site: same-origin`). GETs never change state except the callback, and Home's art cache (`state` `dashboard:art`, written in `waitUntil`).
- **HTTP (src/http.ts):** every HTML response gets a per-response CSP nonce (`style-src 'nonce-…'`, `script-src 'self'`, `font-src 'self'`), `Referrer-Policy: same-origin`, nosniff, no-store, noindex. Markup uses classes only (the CSP blocks `style=`; a test checks it). Keep `same-origin`: `no-referrer` makes browsers send `Origin: null` on same-origin POSTs, which breaks the CSRF check.
- **Settings (src/settings.ts):** registry of keys with type, default, label; precedence per key: `settings` row (dashboard) > `SETTINGS` JSON var (then legacy `fromEnv`) > code default. Rows are stored only when they differ from the layer below; `reset=<key>` deletes one. Invalid values fall through and are listed in `problems`, never thrown. `liked` (default off) has `confirmOn`: switching it on requires `confirm_liked=yes`. `aiEditor` is hidden and forced off without `OPENAI_API_KEY`. `advanced` (default off) shows the Activity nav item and page and the `advancedOnly` settings (`alerts`, `timeZone`) and the Account card; hidden settings aren't posted, so they keep their values. Jobs see settings through `Config.features` / `Config.digests`.
- **Dashboard (src/dashboard):** server-rendered, mobile-first; design tokens (navy glass cards, blue accents) in `tokens.ts`, CSS in `styles/` (one part per page group), concatenated by `styles/index.ts` into the one nonce'd `<style>`. Flash messages use fixed codes (`?ok=` / `?error=` in `FLASH`), never user text. Home (`home-view.tsx`) is fed by `loadHome` (`home-data.ts`: one `db.batch` of ~27 statement builders from `src/db/queries.ts`, including one range count for the year-over-year listening lines) and `fillArt` (`art.ts`: `state` `dashboard:art` cache, at most two Spotify calls with a 2.5 s AbortSignal, written in `waitUntil`; a warm view makes none). Settings (`settings.tsx`) is the control panel, most used first (Playlists, Emails; then General, Spotify, Account with History import and, with Advanced, sign-in; the save bar last, `form="settings"`): `status.ts`'s `loadStatus` (the full plays count lives only there) feeds the Spotify and Problems cards and the status line under each setting (`settings-status.tsx`); those lines' buttons (preview, Recreate) submit hidden forms after the settings form via `form=`, like Reset, because forms don't nest. Charts are server-rendered SVG with CSS-only tooltips and an aria-label summary sentence ("Listening by day" is a smooth line per year, the last five years, with a legend of CSS-only year toggles); the W/M/Y switch is radio inputs + `:has()`; the only client JS is `public/import.js` (the uploader), `public/settings-form.js` (shows the save bar once a setting changed; without it the bar always shows) and `public/tour.js` (the guided tour: a spotlight and a card per step across Home and Settings, driven by `#tour-data` and `?tour=<step>`; on Settings every tour action first saves changed settings with a fetch POST /settings, and stays put with the page's error line if refused). Images: only Spotify's CDNs (`isSpotifyImageUrl` in src/http.ts matches the CSP's img-src). No web fonts: the system font stack. Page changes use cross-document view transitions (CSS only).
- **History import (src/import):** `public/import.js` uploads the zip/JSON to R2 (`IMPORTS`, keys `imports/<id>/<n>.<ext>`) in 10 MiB multipart parts through the Worker; `ImportWorkflow` indexes zips with range reads, stages each entry into `import_plays`, deletes the R2 objects, computes the preview in SQL, waits for approval (`waitForEvent`, 7 days), applies one UTC month per step, enriches metadata, optionally backfills Liked/Frequent (`runSyncFull({limit})`), emails. **The `applied_to` guard is mandatory:** each month's batch (tracks, plays upsert, deletes, staging cleanup, marker) re-checks `status = 'applying' AND applied_to < sliceEnd` in every statement, so a replayed step is a no-op; without it a replay would delete a whole month of plays. **Staging is scoped by import:** `import_plays` has `import_id` (PK `import_id, played_at_ms, track_id`) and every staging read, write and delete filters on it, so a leftover Workflow instance of an older import can't wipe a newer import's rows (an apply over missing staging deletes every play in the month). Before the first month, `checkStaged` requires the staged count to equal `Preview.plays`. Expire, finish and fail only act for the row's current `attempt`. Cancel and retry confirm the attempt's instance has stopped (`stopInstance`/`instanceState`, never swallowing a failed terminate), and instance ids are deterministic (`instanceId`), so a create that errors after creating isn't mistaken for "not started". Preview/apply must match `planReconcile` (src/import/plan.ts, shared with `scripts/import-history.ts`; an equivalence test guards it).
- `src/jobs/*`: each job takes `(config, db, spotifyClient)`. Write-mode gating: `SpotifyClient` blocks Spotify writes unless `WRITE_MODE=live`; jobs skip D1 *state* writes (`playlist_tracks`, `state`, `playlists`, `playlist_removals`, `playlist_exclusions`) in `dry_run`. Metadata (`tracks`, `plays`, `track_artists`, `artists`, `sync_runs`) is always written.
- `src/db/queries.ts`: bulk writes bind one JSON array and expand it with `json_each` (500 rows/statement). Keep it this way; D1 caps queries per invocation (1,000) and bound parameters per query (100).
- `src/db/schema.ts`: migrations. v7 baseline equals the original Python schema and records versions 1-7 (keeps a D1 export loadable by the old Python app); Worker-only changes start at v8. v9 adds the privacy export's per-play fields to `plays` (NULL for API plays). v10: `settings`, `sessions`, `activity`. v11: `imports`, `import_plays`. v12: one sync cursor key, `liked=true` for instances with data, drops the old `reconnect` state. v13: index `plays(track_id, played_at_ms)` for the NOT EXISTS "new to you" queries (digests and Home).
- Owned playlists (`src/jobs/owned-playlists.ts`) are created on first use with ids in `state` `playlist:<key>` (`frequent`, `hindi`, `on_this_day`, `forgotten_favorites`, `holiday`); `off` = deleted in Spotify (the dashboard's Recreate deletes an `off` row). History playlists are rewritten via `replacePlaylistItems` only when the local day/week (the `timeZone` setting) changes; Holiday Favorites is add-only (hindi pattern), recognising songs by title.
- `src/jobs/digest.ts`: weekly digest (Mon-Sun in the owner's time zone, `state` `recap:last_week` = ISO week) and monthly recap (`recap:last_month`), sent through the email binding whenever the key is behind; only `live` sends, dry runs log the HTML. `previewDigest` sends "[Preview]" without touching `recap:*`. Cover art via one batch `GET /tracks?ids=` + `GET /artists?ids=` at send time; failures fall back to placeholder tiles.
- `src/editor/`: optional AI editor for the digests, on when the `aiEditor` setting is on and the `OPENAI_API_KEY` secret is set; `state` `editor:mode`=`off` is a runtime kill switch and `editor:calls:<UTC YYYY-MM>` caps calls at 10/month (counted in every write mode; dry runs and previews call the model too). One OpenAI Responses API call per digest (`gpt-6.1-sol`, strict `json_schema`, `store: false`, plain fetch). The model orders every section with data (`sectionSpecs` marks them all required, so it never drops a chart), adds up to 3/2 highlight cards (`buildEditorInput` drops any about the song of the period), picks a preset theme and writes copy (song titles in “curly quotes”); code computes every number and `validatePlan` rejects any number not in the input. `planDigest` never throws; `composeDigest` in `src/jobs/digest.ts` sends the default layout on any fallback or when the edited HTML is over 100,000 bytes. The period's seasonal theme (`src/email/themes.ts`) applies with or without the editor. Tests inject `fetch` through `EditorConfig`.
- `src/email/`: the email design system (`layout.ts` tokens + shell, `components.ts` blocks/charts). Email HTML only: tables, inline styles, mobile-first with one `min-width:640px` upgrade block; no SVG/JS/positioning. Keep emails < 100 KB (Gmail clips at 102 KB). The vinyl image is a pre-rendered PNG (`public/email/vinyl.png`, source `scripts/vinyl.html`); bump `VINYL_PATH`'s `?v=` when it changes. Account emails (setup link, welcome) are in `src/emails/account.ts`, import emails in `src/import/emails.ts`.
- `scripts/import-history.ts` treats the privacy export as the source of truth for plays (>= 30 s) inside its span: it reconciles (insert/update/delete), it doesn't append. Same semantics as the dashboard import.
- Spotify refresh token lives in D1 `state` (`spotify_refresh_token`), not in a secret, so the Worker can persist rotations.
- The sync cursor is `state` `cursor_after_ms:default` (`SYNC_CURSOR_KEY`); v12 folded older `cursor_after_ms:<playlist id>` keys into it.
- Cron strings are hard-coded in `src/schedule.ts` and must match `[triggers]` in `wrangler.toml`: change both.

## Conventions

- Use the old Spotify endpoints (`PUT /me/tracks`, `POST /playlists/{id}/tracks`, batch `GET /artists?ids=`); the `/me/library` ones failed when audited.
- `artists.genres` must stay in the existing format: use `genresJson()` (Python `json.dumps` style).
- Parity fixtures in `test/parity/*.json` were generated from the original Python code and are frozen. Don't regenerate; add new behavior tests separately.
- Never log or print the refresh token, session tokens, claim nonces, OAuth codes or secrets. Scripts read credentials from `.dev.vars`.
- Everything rendered into dashboard HTML is escaped: JSX text and attributes (Spotify names and errors included), `esc()` in the emails; no user text in redirect URLs.
- Dashboard views are TSX (`hono/jsx`, turned into strings by `render()` in src/dashboard/render.ts), escaped by default. `raw()` only for trusted strings: the CSS, or HTML another view already rendered (e.g. `importSection()`). Still classes only, no `style=`. `.tsx` files live under src/dashboard, src/import and src/auth.

## Gotchas

- **Never add `public/index.html`** (or any file named like a route, e.g. `public/settings.html`): static assets are served before the Worker and would shadow its pages.
- **Test fixtures must avoid gitignored names** such as `Streaming_History*.json` and `endsong*.json` (the export's real file names are ignored so nobody commits their history): name fixtures by shape (`audio-format.json`) or build zips in the test.
- **Never delete a Worker with live crons.** Set `crons = []`, deploy, wait ~15 min, then delete. Doing otherwise orphaned a trigger and stalled cron dispatch account-wide (docs/PORTING.md).
- Cron changes take minutes (up to ~30) to propagate; don't redeploy repeatedly while waiting.
- Spotify has no playlist delete: "deleting" your own playlist only unfollows it, and writes to it still succeed. Detect it by its absence from `GET /me/playlists` (`followedPlaylistIds`), not from write errors.
- Spotify rejects `localhost` redirect URIs: for the local dashboard use `PUBLIC_URL` `http://127.0.0.1:8788` and register `http://127.0.0.1:8788/auth/callback`.
- The first wrangler API call after it refreshes its expired OAuth token can fail with `7403` ("account not valid"); the next call works. `scripts/lib.ts` retries that once.
- `wrangler d1 execute --file` imports are atomic per file; very large single files can fail with `D1_RESET_DO`. Chunk them.
- `wrangler.toml` top level is production. `[env.test]` binds the test D1 with `remote = true` and simulates R2, Workflows and email locally (`wrangler dev` writes each email under `.wrangler/tmp/email/` and logs the path); vitest sets `remoteBindings: false` so tests never touch a remote database. The local Workflows engine logs a "code had hung" error after an instance finishes; the instance status is still `complete`.
- Workers Builds: build command `npm test && npm run configure`, deploy command `npx wrangler deploy -c wrangler.generated.toml`, build variable `DEPLOY_CONFIG` (one-line JSON). A plain `npx wrangler deploy` fails on the template. Create the `<WORKER_NAME>-imports` bucket and its lifecycle rule before the first deploy with imports on (or set `"imports": false`).
